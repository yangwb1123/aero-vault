## 分析摘要

### 任务分解产出

将 5 个方向拆解为 **42 个任务**（每个 2-6h），覆盖从基础设施到集成测试的全链路：

| 方向 | 任务数 | 总工时 | 人周 |
|------|--------|--------|------|
| S3 通知引擎 (D1) | 8 | 26h | 0.65 |
| CDC 流 (D2) | 6 | 17h | 0.43 |
| Active-Active 复制 (D3) | 8 | 30h | 0.75 |
| WASM 触发器 (D4) | 8 | 28h | 0.70 |
| 合规框架 (D5) | 8 | 29h | 0.73 |
| **合计** | **38** | **130h** | **3.25** |

### 实施节奏

**3 人团队 × 5-6 周**，分 4 阶段：

```
Sprint 1 (W1-2): 基础设施 + 通知引擎 + CDC 流    ✅ 并行组 A+B
Sprint 2 (W2-3): 复制基础 + 合规基础               ✅ 并行组 C
Sprint 3 (W3-4): 复制深度 + 合规深度 + WASM 启动   ✅ 并行组 D
Sprint 4 (W5-6): WASM 完成 + 全量集成 + 发布       ✅ 性能压测+文档
```

### 关键风险

| 🔴 高风险 | 🟡 中风险 |
|-----------|-----------|
| Version Vector 冲突检测算法正确性 | SigV4 签名对 SQS/SNS/Lambda 合规性 |
| 环形复制无限循环 | Events 表在 SQLite 高写入性能 |
| WASM 函数安全逃逸 | CDC 大偏移量查询性能 |

### 重要偏离建议

1. **D3 提前**：建议从 Sprint 4 提到 Sprint 2-3 — 单区域是业务连续性硬天花板
2. **D3-T5 增量交付**：先 LWW（2h）再 Version Vector（6h），避免大任务阻塞
3. **WASM 同步 hooks 延后**：异步触发优先交付，同步 hooks（内容修改+ETag重算）复杂度高
4. **配置下沉**：复制规则建议落到 bucket 级（非全局），与 S3 规范一致
