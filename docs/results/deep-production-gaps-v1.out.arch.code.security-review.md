### 1. 关键：MCP stdio 传输绕过所有身份验证

| 字段 | 描述 |
|-------|-------------|
| **分类** | 身份验证 / 授权 |
| **严重性** | **严重** |
| **标题** | MCP stdio 模式在无任何身份验证的情况下运行 |
| **位置** | `internal/mcp/transport.go:17-45` · `internal/mcp/server.go:133` · `cmd/server/main.go:83-99` |

### 2. 关键：响应头注入（通过用户元数据）

| 字段 | 描述 |
|-------|-------------|
| **分类** | 输入验证 |
| **严重性** | **严重** |
| **标题** | 用户元数据值在返回作为 HTTP 响应头之前未进行转义 |
| **位置** | `internal/api/rest/handler.go:293-298` (`writeMetadataHeaders`) · `internal/api/s3compat/handler.go:402-406` (`writeS3ObjectMeta`) |
| **描述** | `PUT /v1/files/*key` 通过 `X-Meta-*` 头（REST）和 `x-amz-meta-*` 头（S3）接受用户元数据。元数据值通过 `writeMetadataHeaders` / `writeS3ObjectMeta` 未经清理地回显。如果元数据值包含 `\r\n` 序列，攻击者可以向响应中注入任意 HTTP 头，甚至拆分响应体（HTTP 响应拆分）。尽管 `_aero_` 前缀的键被跳过，但任何用户提供的键都可能被利用。 |
| **攻击场景** | 上传一个包含元数据文件的对象，例如：`X-Meta-Description: 良性值\r\nSet-Cookie: evil=session`。任何对该对象的 GET/HEAD 请求都会收到被注入 Set-Cookie 的响应，从而使攻击者能够在缓存/浏览器上下文中劫持会话。 |
| **影响** | 响应拆分可能导致缓存投毒、XSS、会话劫持。 |
| **建议** | 在设置 HTTP 头之前，对元数据值进行换行符（`\r\n`、`\n`）的清理或拒绝。添加一个 `strings.ReplaceAll(v, "\n", "")` 或类似的检查，存储在元数据中之前或响应时。理想情况下使用 `net/http` 的 `Header.Set()`，它拒绝无效头值，但在写入之前进行清理是防御性的。 |
| **工作量** | S（< 1 天） |

### 4. 高：SQL LIKE 模式中的通配符注入（键遍历）

| 字段 | 描述 |
|-------|-------------|
| **分类** | 输入验证 |
| **严重性** | **高** |
| **标题** | 用户控制的键前缀可以包含 LIKE 通配符，导致信息泄露/拒绝服务 |
| **位置** | `internal/repository/sql_objects.go:125-132`（`ListObjects` 中的 `key LIKE $3 AND key > $4`） |
| **描述** | `ListObjects` 构建 `key LIKE $3`，其中 `$3 = prefix + "%"`。虽然 prefix 是通过参数化查询提供的，但 SQLite 和 Postgres 的 `LIKE` 都会特殊处理 `%` 和 `_` 通配符。提供 prefix `___` 会匹配任何恰好三个字符的键；`%admin%` 会匹配包含 "admin" 的所有键。这导致攻击者可以列举他们本无权访问的键。此外，优化器扫描整个匹配集可能导致拒绝服务。 |
| **攻击场景** | 攻击者调用 `GET /v1/files?prefix=%`，强制数据库扫描每个活跃行并返回所有键，即使他们只能看见自己租户内的键（因为 WHERE 子句限制了 tenant_id）。 |
| **影响** | 信息泄露（枚举租户内每个键）；拒绝服务（在数据集大时进行全面扫描）。 |
| **建议** | 在用于 LIKE 之前，对 prefix 中的 `%` 和 `_` 字符进行转义：`prefix = strings.ReplaceAll(prefix, "%", "\\%"); strings.ReplaceAll(prefix, "_", "\\_")`。或者，对于完全安全的键列举，使用 `key >= $3 AND key < $4` 而不是 LIKE。 |
| **工作量** | S（< 1 天） |

## STRIDE 分析摘要

| 威胁 | 风险 | 关键发现 |
|-------|------|-------------|
| **S**poofing（欺骗） | **高** | MCP stdio 没有身份验证；JWT 受众验证缺失；环境变量中的 SigV4 明文凭据 |
| **T**ampering（篡改） | **中等** | SSE AES-256-GCM 保护存储中的数据；HMAC 保护 webhook；但是支持 ETag 读取验证但未默认启用 |
| **R**epudiation（抵赖） | **中等** | 只有管理操作被审计；缺少对象 CRUD 审计追踪 |
| **I**nformation Disclosure（信息披露） | **高** | 错误消息泄露内部细节；元数据 header 注入泄漏；webhook 失败包含完整负载；SQL LIKE 通配符枚举 |
| **D**enial of Service（拒绝服务） | **中等** | MCP HTTP 绕过速率限制；`JOBS_MAX_DEPTH=0` 允许无限任务积压；SQL LIKE `%` 前缀会导致全表扫描 |
| **E**levation of Privilege（权限提升） | **严重** | MCP stdio 作为“默认”管理员运行；无身份验证时管理端点未受限制；JWT 签发不检查租户边界 |

## 最终总结

| 指标 | 值 |
|--------|-------|
| **整体安全态势** | **需要改进** |
| 已发现严重问题 | 2 |
| 高严重性问题 | 4 |
| 中等严重性问题 | 5 |
| 低/信息性问题 | 4 |
| **总计** | **15** |

### 前三大严重问题
1. **MCP stdio 没有身份验证** — 对本地进程的完全未认证访问
2. **元数据 header 注入** — 通过未经清理的元数据值进行 HTTP 响应拆分
3. **无身份验证时的管理端点暴露** — 默认配置中无需凭据即可获得完全的管理员权限

### 前三项速赢（高影响力，低工作量）
1. **添加安全头** — 实现一个中间件，在所有响应上设置 `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer`（1 小时）
2. **清理错误消息** — 屏蔽未分类错误中的内部 `err.Error()` 详情（2 小时）
3. **清理元数据值中的换行符** — 防止所有元数据 header 写入路径中的 header 注入（1 小时）

### 安全债务
- 应用层没有 TLS（假设反向代理）
- 缺少对象级审计追踪
- 不支持持久化密钥的跨副本密钥撤销（无 Postgres）
- 没有默认启用读时完整性验证
- 没有限制未登录用户的速率限制配置
- 没有配置 JWT 签发者和受众验证
