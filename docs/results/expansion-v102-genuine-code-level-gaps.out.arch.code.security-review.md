# 安全审查：aero-vault — 对象存储 + AI/RAG 平台

| 元数据 | 值 |
|--------|-------|
| **存储库** | `github.com/aero-vault/aero-vault` |
| **语言** | Go 1.25 |
| **审查版本** | HEAD（2026-07-12） |
| **代码行数** | ~15,000 行 Go |
| **架构** | REST / S3 兼容 / WebDAV / MCP 适配器 → FileService → 存储 + 仓库 |
| **审查者** | 首席安全工程师 |

---

## 执行摘要

aero-vault 展示了在现代 Go 中编写安全感知代码的良好基础。使用参数化查询（SQL 占位符）是正确完成的，安全标准（AES-256-GCM，SHA-256 HMAC）是强有力的，并且密钥轮换架构设计得很巧妙。但是，存在一些严重的安全问题需要立即关注，尤其是在**默认情况下身份验证未启用**、**客户端控制的租户**以及**存储了硬编码的弱默认密钥**方面。

**总体安全态势：需要改进**

---

## 详细发现

### 🔴 发现 1：默认情况下身份验证已禁用（关键）

| 字段 | 值 |
|-------|-------|
| 类别 | 身份验证 |
| 严重性 | **严重** |
| 标题 | AUTH_KEYS 为空时系统完全开放 |
| 位置 | `internal/auth/auth.go:42-50`，`internal/auth/auth_middleware.go:21-26` |
| 描述 | 当 `AUTH_KEYS` 环境变量为空（或未设置）时，`Parse("")` 返回一个已禁用 pass-through 的 registry。所有路由——包括 `/v1/admin/keys`、`/v1/admin/tenants`、`PUT /v1/files/*`——都无需凭证即可访问。将 AUTH_KEYS 留空是默认的 `.env.example` 值。 |
| 攻击场景 | 攻击者发现一个运行 aero-vault 的实例，该实例配置了默认值。他们可以列出所有 API 密钥、创建新的管理员密钥、读取/写入/删除所有对象以及访问 AI 检索，而无需任何身份验证。 |
| 影响 | 完全接管数据存储。可以导出所有数据、注入恶意内容以及消耗 AI 预算。 |
| 建议 | **在生产部署之前强制要求身份验证。** 至少：验证 AUTH_KEYS、AUTH_JWT_SECRET 或 S3_SIGV4_CREDENTIALS 中至少有一个已配置。向 `config.Validate()` 添加启动时检查：`if c.Auth.Keys == "" && c.Auth.JWTSecret == "" && c.Auth.SigV4Credentials == "" { return error("production: at least one auth method required") }` |
| 工作量 | **S**（新增 ~10 行配置验证） |

### 🔴 发现 2：硬编码的弱签名密钥（高）

| 字段 | 值 |
|-------|-------|
| 类别 | 密码学 / 配置 |
| 严重性 | **高** |
| 标题 | `.env.example` 包含 `STORAGE_LOCAL_SIGN_KEY=change-me` |
| 位置 | `.env.example:16` |
| 描述 | 本地预设 URL 的 HMAC 签名密钥的默认值为 `"change-me"`。如果部署者将 `.env.example` 原样复制到 `.env`（许多团队就是这么做的），预设 URL 签名密钥就是一个众所周知的弱密钥。攻击者可以伪造预设 URL。 |
| 攻击场景 | 攻击者知道预设密钥 `"change-me"`。他们生成一个预设 GET URL 以访问他们本无法访问的任何对象，或一个预设 PUT URL 以覆盖任意对象。 |
| 影响 | 绕过身份验证/授权进行对象读取和写入。 |
| 建议 | 1. 如果未设置 `STORAGE_LOCAL_SIGN_KEY`，则在启动时生成一个随机密钥。2. 或者，如果密钥未从默认值更改，则在启动时记录警告。3. 记录生产部署始终更改此值的要求。 |
| 工作量 | **S**（启动时生成随机密钥） |

### 🔴 发现 3：API 密钥明文在 URL 中泄露（严重）

| 字段 | 值 |
|-------|-------|
| 类别 | 数据保护 / 身份验证 |
| 严重性 | **高** |
| 标题 | DELETE /v1/admin/keys/{token} 将 API 令牌放在 URL 路径中 |
| 位置 | `internal/api/rest/admin.go:166-175`，`internal/api/rest/router.go:80` |
| 描述 | 撤销 API 密钥的端点将完整的明文 API 令牌作为 URL 路径参数传递：`DELETE /v1/admin/keys/{token}`。令牌出现在服务器访问日志、反向代理日志、浏览器历史记录和 `Referer` 头中。 |
| 攻击场景 | 管理员撤销泄露的密钥。访问日志的处理者现在拥有明文令牌，可用于未经授权访问。 |
| 影响 | 日志泄露后，API 密钥保密性完全丧失。 |
| 建议 | 改为在请求体中使用密钥哈希（或随机撤销 ID）传递令牌，或对其进行 HMAC 处理。创建一条通过撤销 ID 引用密钥的撤销路径，而不是直接使用明文令牌。 |
| 工作量 | **M**（~1 天用于新端点 + 迁移） |

### 🔴 发现 4：客户端控制的租户标头（严重）

| 字段 | 值 |
|-------|-------|
| 类别 | 授权 |
| 严重性 | **高** |
| 标题 | X-Aero-Tenant 标头完全由客户端控制 |
| 位置 | `internal/middleware/middleware.go:44-54` |
| 描述 | 租户上下文完全来自 `X-Aero-Tenant` HTTP 请求标头，没有服务器状态验证。任何客户端都可以将其设置为任何值。虽然授权中间件*确实*为通过身份验证的密钥固定租户（`auth_middleware.go:103-107`），但匿名公共读取路径（`anonRead`）直接传递租户标头，并且未启用身份验证时的回退路径（`!r.Enabled()`）也是如此。 |
| 攻击场景 | 场景 A（Auth 关闭）：攻击者发送 `X-Aero-Tenant: victim-corp` 以访问/修改其他租户的数据。场景 B（匿名公共读取）：攻击者发送 `X-Aero-Tenant: victim-corp`，如果受害者对象标记为公共读取，则读取它们。 |
| 影响 | 完全绕过租户隔离——跨租户数据访问。 |
| 建议 | 将租户解析移至身份验证中间件内。对于未经身份验证的请求，租户应默认为 `"anonymous"` 或系统默认值，并且永远不允许通过标头覆盖。在 Pass-through 模式下，要求 `X-Aero-Tenant` 仅适用于管理员预共享密钥与特定租户绑定的情况（如代码中的 `auth_middleware.go` 所做）。 |
| 工作量 | **S**（更改租户中间件以在未启用身份验证时拒绝客户端租户） |

### 🟠 发现 5：预设签名不含过期验证（中等）

| 字段 | 值 |
|-------|-------|
| 类别 | 密码学 |
| 严重性 | **中等** |
| 标题 | 本地预设方案对过期时间字段无保护 |
| 位置 | `internal/storage/sign.go:8-15` |
| 描述 | `signLocal` 函数使用 HMAC-SHA256 签署 `method\nobjectKey\nexpires`，但没有权威的时间源。预设 URL 包含 `expires` 参数，但签名的方案从未被验证为抵抗重放——任何拥有签名 URL 的人都可以在任意时间使用它，因为过期信息仅嵌入在 URL 本身中，且验证代码可能依赖于 `time.Now()` 与请求接收时间的比较。 |
| 攻击场景 | 预设 GET URL 有效期为一小时：共享它的接收者可以在签名 URL 失效后很长时间内继续使用它，具体取决于存储层的实现。实际上，生成的 URL 的 `expires` 字段仅由返回给客户端的 JSON 中的客户端时间知道。 |
| 影响 | 预设 URL 可能存活时间超过预期，导致意外的数据访问。 |
| 建议 | 1. 将 `expires` Unix 时间戳嵌入签名有效载荷中（已完成）。2. 在存储层添加验证：当当前的 `time.Now()` 超过签署的过期时间时拒绝请求。 |
| 工作量 | **S**（在验证路径中添加 `time.Now()` 检查） |

### 🟠 发现 6：缺少安全响应头（中等）

| 字段 | 值 |
|-------|-------|
| 类别 | 合规 |
| 严重性 | **中等** |
| 标题 | HTTP 响应中不存在安全头 |
| 位置 | 全局 — `cmd/server/main.go` |
| 描述 | 应用程序未设置以下安全头：`Strict-Transport-Security`、`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Content-Security-Policy`。如果用户通过浏览器访问 `/ui` 或 `/docs`，这会使他们面临攻击。 |
| 攻击场景 | 如果应用程序是通过 HTTPS 服务的，缺少 HSTS 会使用户容易受到 SSL 剥离攻击。缺少 `X-Content-Type-Options` 可能会允许 MIME 类型混淆攻击。 |
| 影响 | XSS、MIME 嗅探、点击劫持。 |
| 建议 | 添加一个中间件来设置安全头。在 `applyMiddleware` 函数的 `cmd/server/main.go` 中：`{"security_headers", securityHeadersMiddleware}`，它至少设置 `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`，以及当 `X-Forwarded-Proto: https` 或配置要求时的 `Strict-Transport-Security`。 |
| 工作量 | **S** |

### 🟠 发现 7：Webhook 失效信件状态混淆（中等）

| 字段 | 值 |
|-------|-------|
| 类别 | 威胁建模 / 数据完整性 |
| 严重性 | **中等** |
| 标题 | Webhook 失效信件使用 `MarkWebhookSucceeded` 来停止重试 |
| 位置 | `internal/events/webhook.go:196-199` |
| 描述 | 经过 10 次重试后，webhook 重试代码调用 `MarkWebhookSucceeded` 来停止进一步重试。这用“成功”状态掩盖了永久性故障。在监控中，一个实际上失败的 webhook 看起来是成功的。 |
| 攻击场景 | webhook 目标被破坏并拒绝所有事件。操作员仅监控成功，永远不会意识到事件没有被送达。 |
| 影响 | 事件丢失。Webhook 兼容性/安全监控被破坏。 |
| 建议 | 添加一个 `webhook_failures` 状态列，其值为 `pending` / `succeeded` / `dead_lettered`。在失效信件时，更新为 `dead_lettered` 而不是 `succeeded`。更新 `NextPendingFailures` 仅选择 `pending` 行。 |
| 工作量 | **S**（添加列 + 迁移） |

### 🟠 发现 8：X-Request-ID 注入（中等）

| 字段 | 值 |
|-------|-------|
| 类别 | 输入验证 / 日志伪造 |
| 严重性 | **中等** |
| 标题 | X-Request-ID 在未经验证/清理的情况下被接受 |
| 位置 | `internal/middleware/middleware.go:32-36` |
| 描述 | 中间件接受客户端提供的 `X-Request-ID` 头，如果存在则直接使用它，而不是生成一个新的 UUID。该值会在未清理的情况下写回 `X-Request-ID` 响应头。它还会传播到日志、事件有效载荷和审计线索。 |
| 攻击场景 | 攻击者发送 `X-Request-ID: \n[malicious log entry]`。日志解析器（基于 JSON 的日志记录缓解了部分问题，但基于文本的日志记录则不能）可能会错误解析。日志伪造可能掩盖恶意活动。 |
| 影响 | 日志注入。日志分析/取证被破坏。 |
| 建议 | 验证输入格式：如果非空，确保它匹配 `^[a-zA-Z0-9._-]+$`。总是生成一个 UUID 并将其设置在响应头中——客户端提供的值可以存储在单独的上下文字段中，或者完全被忽略。 |
| 工作量 | **S** |

### 🔵 发现 9：SQL LIKE 中数据库端未进行彻底转义（低）

| 字段 | 值 |
|-------|-------|
| 类别 | 输入验证 |
| 严重性 | **低** |
| 标题 | SQL LIKE pattern 使用用户前缀且未转义 |
| 位置 | `internal/repository/sql_objects.go:89-96` |
| 描述 | ListObjects 查询构建为 `key LIKE $3 AND key > $4`，其中 `$3 = prefix + "%"`。虽然参数化可以防止 SQL 注入，但 `prefix` 本身如果包含 `%` 或 `_` 通配符则不会转义，这可能导致意外的模式匹配。 |
| 攻击场景 | 用户列出带有前缀 `secret%` 的对象，并看到带有文字 `secret%` 的对象——行为正确。但使用前缀 `%confidential%`，可能会列出他们不应看到的对象，如果授权依赖于基于前缀的模式匹配。 |
| 影响 | 意外的对象枚举。低严重性，因为授权在服务层处理。 |
| 建议 | 使用 `strings.ReplaceAll(prefix, "%", "\\%")` 和 `strings.ReplaceAll(prefix, "_", "\\_")` 并在 SQL 中使用 `ESCAPE '\'`。 |
| 工作量 | **S** |

### 🔵 发现 10：内存 DoS — 速率限制器映射（低）

| 字段 | 值 |
|-------|-------|
| 类别 | 威胁建模 / DoS |
| 严重性 | **低** |
| 标题 | 具有宽松边界的大速率限制器映射 |
| 位置 | `internal/middleware/ratelimit.go:39` |
| 描述 | 速率限制器每个唯一租户创建一个桶条目，最大为 50,000 个条目。租户密钥是 `X-Aero-Tenant` 头的值（客户端控制）。在启用身份验证的情况下，租户由中间件固定，但未启用身份验证时，攻击者可以发送 50,000 个唯一的租户值，消耗约 50MB+ 内存。 |
| 攻击场景 | 攻击者发送 50,000 个请求，每个请求使用唯一的 `X-Aero-Tenant: attacker-XXXXX` 值，填充 50k 桶映射。进一步具有新租户值的请求被拒绝。50,000 个 *唯一* 值的 DoS 限制了合法租户的速率限制容量。 |
| 影响 | 拒绝服务（有限）。50k 是 configurable，但仍然很高。 |
| 建议 | 1. 在身份验证将租户固定到经过身份验证的主体之前，不要使用租户进行速率限制。2. 将默认值降低到 10,000 并记录。3. 在未启用身份验证的情况下，对所有请求使用单个 `"default"` 桶。 |
| 工作量 | **S** |

### 🔵 发现 11：PII 检测器正则表达式过于宽泛（低）

| 字段 | 值 |
|-------|-------|
| 类别 | 数据保护 |
| 严重性 | **低** |
| 标题 | PII 检测器中的电话和 IP 正则表达式产生假阳性 |
| 位置 | `internal/ai/pii.go:52-53` |
| 描述 | 电话号码正则表达式 `(?:\+\d{1,3}[\s\-]?)?(?:\(?\d{2,4}\)?[\s\-]?){2,4}\d{2,4}` 匹配许多非电话数字序列（例如，版本字符串 `1.2.3.4`）。IP 正则表达式 `\b(?:\d{1,3}\.){3}\d{1,3}\b` 匹配任何点分四组数字，包括类似 `999.999.999.999` 的无效 IP 和类似 `100.100.00.01` 的私有 IP。 |
| 攻击场景 | PII 扫描报告许多假阳性。对象被标记为包含 PII 并被错误地从搜索索引中排除或进行脱敏处理。 |
| 影响 | 搜索质量下降；对文本进行不必要的脱敏处理。 |
| 建议 | 收紧正则表达式。对于电话，需要国家代码或有效的本地前缀。对于 IP，在应用规则之前验证八位字节范围（0-255）。使用 `net.ParseIP` 进行验证，或切换到更严格的模式。 |
| 工作量 | **S** |

| 字段 | 值 |
|-------|-------|
| 类别 | 数据保护 |

## STRIDE 分析

### 欺骗

| 威胁 | 状态 | 备注 |
|-------|--------|-------|
| 伪造 JWT | ✅ **已减轻** | HS256 签名已在 `auth/jwt.go` 中验证。使用 `crypto/hmac` 且 `hmac.Equal` 可防定时攻击。 |

## 建议摘要

### 🔥 前 3 个关键问题（按风险排序）

1.  **🔴 身份验证默认已禁用** — 修复：向 `config.Validate()` 添加检查，要求在生产环境中至少设置一种身份验证方法。
2.  **🔴 客户端控制的租户** — 修复：将租户解析移入身份验证中间件；当身份验证未启用时不允许任意租户头。
3.  **🔴 API 密钥在 URL 中泄露** — 修复：将 `DELETE /v1/admin/keys/{token}` 更改为通过体或撤销令牌接受令牌哈希。

### ⚡ 前 3 个速效方案（高影响力 / 低工作量）

1.  **安全头中间件** — 添加 `Strict-Transport-Security`、`X-Content-Type-Options`、`X-Frame-Options`。~20 行代码。
2.  **X-Request-ID 验证** — 净化或忽略客户端提供的 `X-Request-ID` 值。~5 行代码。
3.  **Webhook 失效信件状态** — 添加 `dead_lettered` 状态并更新查询以排除它。~30 行代码 + 1 个迁移脚本。

## 结论

**总体安全态势：需要改进**

代码库建立了*优秀的密码学基础*（AES-256-GCM 信封、HMAC-SHA256、适当的随机数生成），但**核心访问控制模型存在根本性缺陷**。默认情况下身份验证已禁用，加上客户端控制的租户头，意味着默认部署对任何知道端点的人都是完全开放的。默认的预设签名密钥 `"change-me"` 是一个经典的陷阱。

积极的一面：
- ✅ 通过参数化查询实现 SQL 注入防护
- ✅ SSE 密钥轮换设计得很好（信封 + 密钥 ID → 无需重写）
- ✅ 速率限制和并发控制已实现（每个租户限流）
- ✅ JWT `ten` 声明是必需的（防止意外升级）
- ✅ 管理操作有审计线索
- ✅ 代码库遵循扎实的工程实践

在将任何面向互联网的实例投入生产之前，必须修复前 3 个关键问题。
