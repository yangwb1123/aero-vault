# 安全审查报告：Aero-Vault 对象存储系统

## 审查范围
- **目标：** 整个代码库，涵盖 REST API、S3 兼容层、WebDAV、MCP、AI/RAG、存储加密、身份验证、速率限制和中间件
- **代理：** 在所有功能路径上模拟对抗性条件
- **基于：** OWASP Top 10（2021）、NIST SP 800-53、STRIDE

## 发现

### 查找 #1 — 关键

| 字段 | 详情 |
|-------|--------|
| **类别** | 加密 / 身份验证 |
| **严重性** | **严重** |
| **标题** | 预签名 URL 签名密钥在配置中硬编码了可预测的默认值 |
| **位置** | `.env.example` 第 9 行：`STORAGE_LOCAL_SIGN_KEY=change-me`；`internal/storage/sign.go` |
| **描述** | `STORAGE_LOCAL_SIGN_KEY` 环境变量用于 HMAC 签名预签名 URL（来自 `sign.go`）。示例配置硬编码了 `"change-me"`，作为文档中的默认值。任何将默认值部署到生产环境的实例都会暴露对象的读/写访问权限，而无需身份验证。 |
| **攻击场景** | 1) 攻击者发现使用默认 `change-me` 键的服务器。2) 他们查询公开的 `/v1/files` 路径以获取对象键。3) 他们伪造预签名 URL：`GET /v1/files/secret.pdf?expires=9999999999&sig=<HMAC-forged>`。4) 他们可以读取或写入任何对象，而无需经过身份验证或授权。 |
| **影响** | 完全数据泄露（读取）和覆盖（写入）。预签名 URL 可被伪造，从而绕过整个身份验证和授权层。 |
| **建议** | 1) 在代码中移除硬编码的默认值。2) 在 `config.go` 中实施启动时检查：如果 `PublicURL` 已设置但 `SignKey` 是默认值或为空，则抛出一个清晰的错误。3) 强制最小密钥长度（> 16 字节）。4) 记录一个强大的生成命令：`openssl rand -hex 32`。 |
| **工作量** | S（< 1 天） |

### 查找 #2 — 关键

| 字段 | 详情 |
|-------|--------|
| **类别** | 威胁模型 / 输入验证 |
| **严重性** | **严重** |
| **标题** | SigV4 分块流式传输绕过逐块签名验证 |
| **位置** | `internal/auth/sigv4_chunk.go` 第 14-16 行：注释内容 "Per-chunk signatures are not re-verified" |
| **描述** | `decodeStreamingBody` 对 AWS 分块编码的正文进行解块，但*不*验证每个块的签名。初始签名是在 Authorization 头中验证的，但攻击者可以在初始验证通过后，在到达实际处理程序之前修改正文块。 |
| **攻击场景** | 1) 上传对象的客户端使用 SigV4 分块编码发送初始头。2) 代理或中间盒拦截并修改 X-Amz-Content-Sha256 头为 `STREAMING-AWS4-HMAC-SHA256-PAYLOAD`。3) 分块解码器剥离签名并将被篡改的块馈送到服务层。4) 存储了不同的对象内容，且未被检测到。 |
| **影响** | 存储的数据完整性受损。无法检测到传输中的数据篡改。用户无法信任已存储对象的完整性。 |
| **建议** | 实现可选的分块签名验证（根据 `Content-Encoding: aws-chunked` + `x-amz-trailer`）。或者，要求所有 SigV4 上传在非分块模式（`X-Amz-Content-Sha256: <hex>`）下进行完整的正文 SHA256，或者完全拒绝对关键/审计工作负载的分块编码。记录此限制。 |
| **工作量** | M（1-3 天） |

### 查找 #3 — 高

| 字段 | 详情 |
|-------|--------|
| **类别** | 数据保护 |
| **严重性** | **高** |
| **标题** | API 密钥以明文形式存储在内存中，Dump 攻击可窃取 |
| **位置** | `internal/auth/auth.go` 第 39-41 行：`type Key struct { Token string ... }`；以及 `Registry.keys map[string]Key` |
| **描述** | `Registry.keys` 映射将 API 密钥令牌以其原始明文形式存储在内存中。虽然令牌在被传入 `AddKey()` 后从函数栈中暴露的时间很短，但运行中的进程如果在核心转储、`/proc/self/mem` 或通过调试器接口被入侵，可能会泄露密钥。具有本地访问权限的攻击者可以转储所有当前有效的 API 密钥。 |
| **攻击场景** | 1) 攻击者通过容器逃逸或 RCE 在服务器上获得代码执行。2) 他们读取 `/proc/<pid>/mem` 或触发核心转储。3) 他们解析进程内存以定位 `Registry.keys`。4) 他们恢复所有明文 API 密钥（静态 + 持久化），并获得对系统的永久访问权限。 |
| **影响** | 所有 API 密钥完全泄露。攻击者保留持久访问权限。 |
| **建议** | 1) 使用 `[]byte` 并在使用后立即清除（零化）。2) 在密钥生命周期内尽可能短地保留纯文本令牌——在查找时对其进行哈希处理，并将哈希作为键。3) 在 Go 1.24+ 上考虑使用 `goexperiment.execheapsanitize` 或 `runtime.BoundsCheck` 等带外敏感指针。4) 如果可能，对服务间密钥使用短暂的 JWT 而不是长期存在的 API 密钥。 |
| **工作量** | M（1-3 天） |

### 查找 #4 — 高

| 字段 | 详情 |
|-------|--------|
| **类别** | 身份验证 / 会话管理 |
| **严重性** | **高** |
| **标题** | JWT 签发没有最大 TTL 限制，允许永久有效令牌 |
| **位置** | `internal/api/rest/admin.go` 第 105-112 行：`IssueJWT` 处理程序；`internal/auth/jwt.go` 第 118-120 行 |
| **描述** | `POST /v1/admin/jwt` 管理端点接受 `ttl_seconds` 字段，且没有上限。可以签发 TTL 为 0（无限期）或数十年（`2^31-1` 秒 = 68 年）的令牌。由于 JWT 撤销通常很困难（尤其是在无状态配置中），这构成了一个重大的密钥管理风险。 |
| **攻击场景** | 1) 管理员（或其自动化工具）使用 `ttl_seconds: 315360000`（10 年）签发 JWT。2) 该管理员被解雇。3) 其凭据不会被轮换（没有人记得这个长期存在的 JWT）。4) 攻击者以某种方式获得了此 JWT 的访问权限（日志、泄露的 CI/CD 变量、遗留配置）。5) 他们可以在 10 年内以该租户的身份进行身份验证。 |
| **影响** | 无限期未经授权的访问，难以撤销。 |
| **建议** | 1) 对管理签发的 JWT 实施最大 TTL（例如，`MAX_JWT_TTL=86400` 秒或 `MAX_JWT_TTL_HOURS=24`）。2) 添加启动时配置以限制最大允许 TTL。3) 考虑通过数据库/Redis 进行 JWT 撤销检查（黑名单），至少对于长期存在的令牌。 |
| **工作量** | S（< 1 天） |

| 字段 | 详情 |
|-------|--------|
| **类别** | 速率限制 / DoS |
| **严重性** | **中** |
| **标题** | 速率限制器使用客户端控制的租户头作为键——允许自选桶 |
| **位置** | `internal/middleware/ratelimit.go` 第 107-112 行：`func (rl *RateLimiter) isAllowed(ctx context.Context)` 和 `TenantFrom(ctx)` |

| **描述** | `STORAGE_SSE_REWRAP_ON_START` 在启动时触发的函数在一个 goroutine 中运行，但任何失败只会记录一个警告。如果关键错误（权限问题、无效信封）发生，操作员可能不会注意到，这会导致旧的（可能是泄露的）加密密钥仍然有效，并且可被用于解密数据。 |

## 总结

| 领域 | 评估 |
|--------|-----------|
| **整体安全态势** | **需要改进** |
| **关键问题** | 2（严重） |
| **高严重性问题** | 4 |
| **中严重性问题** | 3 |
| **低/信息性问题** | 4 |

### 前 3 个关键问题

1. **默认预签名签名密钥（严重）** — `STORAGE_LOCAL_SIGN_KEY=change-me` 使得任何发现此配置的实例都可以伪造预签名 URL。这是最紧急的问题，因为默认值记录在 starter 配置中，可能会被不加选择地部署。

2. **SigV4 分块签名绕过（严重）** — 上传的分块正文中的逐块 HMAC 不会被重新验证。在初始签名验证通过后，中间代理可以篡改存储的数据。

3. **API 密钥在内存中以明文形式存储（高）** — 所有活动 API 密钥的明文都保留在进程堆中。进程内存转储或远程代码执行将恢复所有密钥。

### 前 3 个速赢项目（高影响，低工作量）

| # | 修复 | 工作量 | 影响 |
|---|------|--------|--------|
| 1 | 添加安全头（CSP、HSTS、X-Content-Type-Options、X-Frame-Options）| < 1 天 | 立即缓解 Web UI 用户的 XSS/点击劫持 |
| 2 | 使用泛化消息替换详细的内部错误 | < 1 天 | 阻止架构/路径/供应商泄露 |
| 3 | 对管理 JWT 签发实施最大 TTL 限制 | < 1 天 | 防止永久有效令牌 |

### 安全债务

1. **SigV4 分块签名验证** — 存储系统中的关键完整性空白。随着系统的成熟，这是一个高风险的重构项。
2. **速率限制器键空间** — 需要使用户/租户/IP 的速率限制成为多层的。目前基于头部的键控是一个已知的问题。
3. **MCP 工具审计** — 代理工具调用路径缺少审计，使得检测和取证变得困难。
4. **SSE 重写弹性** — 密钥轮换后的启动重写过程中，异步错误处理静默吞下异常。
5. **PII 检测器准确性** — 正则表达式过于宽泛，面临在高频使用中产生高误报率的风险，需要改进。
