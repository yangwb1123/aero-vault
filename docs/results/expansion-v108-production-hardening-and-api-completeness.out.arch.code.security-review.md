## 1. 认证与授权

### 发现 #1 — 静态 API 密钥以明文形式存在于进程内存中

| 字段 | 描述 |
|-------|-------------|
| **类别** | 数据保护 / 加密 |
| **严重性** | **高** |
| **标题** | `AUTH_KEYS` 中的静态 API 密钥以明文形式存在于 `Registry.keys` 映射中 |
| **位置** | `internal/auth/auth.go:67-95`（`Parse` 函数），`internal/auth/store.go:34-38`（`HashToken` —— 仅用于持久化密钥路径） |
| **描述** | 环境密钥（通过 `AUTH_KEYS`）解析为 `map[string]Key` 并以明文形式存在于进程内存中。没有内存加密或 `sodium`/`memguard` 保护。虽然持久化的 API 密钥通过 SHA-256 哈希（`store.go:34-38`）存储，但环境变量密钥从未被哈希——它们作为明文令牌字符串保留。`/proc/[pid]/environ`、核心转储 (core dump) 或进程内存转储会泄露所有配置的令牌。 |
| **攻击场景** | 攻击者获得同一主机上的代码执行权限 → 读取 `/proc/[pid]/maps` + `/proc/[pid]/mem` → 提取 `AUTH_KEYS` 映射的内容 → 获得对所有租户的持久 API 访问。 |
| **影响** | 完全的认证绕过；攻击者获得与配置密钥相同的访问权限。 |
| **建议** | 1) 通过 SHA-256 哈希所有令牌（即使是环境令牌）并在匹配前对输入进行哈希。这很复杂，因为令牌是直接比较的。2) 短期内，在不再需要时对内存中的密钥缓冲区进行清零（Go 无法很好地处理这个问题）。3) 记录文档说明 `AUTH_KEYS` 适用于小型/开发部署；生产环境应使用持久化、已哈希的密钥路径（`AUTH_PERSIST_KEYS=true`）。 |
| **工作量** | M（1-3 天） |

### 发现 #2 — SigV4 秘密密钥以明文形式存在于进程内存中

| 字段 | 描述 |
|-------|-------------|
| **类别** | 数据保护 / 加密 |
| **严重性** | **高** |
| **标题** | `S3_SIGV4_CREDENTIALS` 中的 SigV4 秘密密钥以明文形式存在于 `SigV4Verifier.creds` 中 |
| **位置** | `internal/auth/sigv4.go:33-39`（`sigV4Cred` 结构体），第 44-70 行（`ParseSigV4Credentials`） |
| **描述** | SigV4 秘密密钥以 Go 字符串形式解析，与静态 API 令牌相同。Go 字符串是不可变的，在 GC 之前一直存活，并且不能被零化。秘密密钥用于派生每次请求的签名密钥，但它们在进程的整个生命周期内保留在内存中。 |

| **攻击场景** | 与 #1 相同 —— 一旦获得代码执行权限，提取 `SigV4Verifier.creds` 映射 → 获取 AWS SigV4 秘密密钥 → 为任何 S3 操作签名请求。 |
| **影响** | 完全的 S3 兼容 API 访问，能够读取、写入和删除任何对象。 |
| **建议** | 与 #1 相同的缓解措施。考虑分离短暂的签名密钥并轮换 `S3_SIGV4_CREDENTIALS`。 |
| **工作量** | M（1-3 天） |

### 发现 #3 — JWT 令牌是唯一载体，缺乏客户端绑定

| 字段 | 描述 |
|-------|-------------|
| **类别** | 认证 |
| **严重性** | **中** |
| **标题** | JWT 令牌本身足以进行 API 访问；没有 TLS 绑定量（`cnf`、`x5t`）或客户端 IP 指纹 |
| **位置** | `internal/auth/jwt.go:105-140`（`Verify` 方法） |
| **描述** | JWT 验证仅检查签名、过期时间和颁发者。没有 `cnf`（确认）声明将令牌绑定到特定的 TLS 连接或客户端。这意味着被窃取的 JWT（通过日志泄露、中间人攻击、浏览器 XSS）可以被攻击者无限期使用，直到过期。 |
| **攻击场景** | 攻击者拦截或窃取 JWT（例如，从不安全的日志、XSS 攻击、TLS 中间人 → 在没有正确证书固定的网络上）→ 使用窃取的令牌调用 API → 以受害者身份获得完全认证访问。 |
| **影响** | 令牌泄露导致完全的认证绕过。 |
| **建议** | 1) 强制要求 TLS（检查 `req.TLS` 并拒绝非 TLS 连接上的令牌）。2) 实施可选的令牌绑定：使用 TLS 客户端证书指纹（`x5t#S256`）或 OAuth 演示的 `cnf` 声明。3) 使用短 TTL（当前 `Sign` 没有默认 TTL —— `claims.Exp` 仅在 `TTL > 0` 时设置），并鼓励令牌刷新。 |
| **工作量** | L（> 3 天，用于完整的令牌绑定） |

### 发现 #4 — 模拟租户标头绕过租户隔离

| 字段 | 描述 |
|-------|-------------|
| **类别** | 授权 |
| **严重性** | **高** |
| **标题** | 传入的 `X-Aero-Tenant` 标头在认证中间件中被信任 |
| **位置** | `internal/auth/auth_middleware.go:86-93`（`authenticateBearer` 中的租户提取）和 `internal/middleware/middleware.go:52-60`（`Tenant` 中间件） |
| **描述** | 租户身份来源于 `X-Aero-Tenant` 请求标头。虽然认证中间件在从已验证密钥的租户匹配后将此标头设置为 `key.Tenant`，但标头最初是由客户端提供的。在认证之前，`Tenant` 中间件（在 `Auth` 之前运行）在 `X-Aero-Tenant` 标头缺失或为空时回退到 `"default"`。这意味着未认证的请求可以在 `Auth` 中间件拒之门外之前获得 `"default"` 租户上下文。此外，拥有租户 `"*"`（管理员）密钥的客户端可以**在原始标头中设置任何租户**，绕过租户隔离。 |
| **攻击场景** | 攻击者 A（租户 `"evil"` 的有效密钥）发送 `X-Aero-Tenant: victim` → 如果密钥的租户是 `"*"`（管理员），攻击者获得对 `"victim"` 数据的访问权限。或者：未认证的请求到达时携带 `X-Aero-Tenant: victim` → `Tenant` 中间件在请求到达 `Auth` 之前设置 `ctx` → 如果在 `Auth` 之前运行的任何中间件使用了 `TenantFrom()`，则敏感信息可能会泄露。 |
| **影响** | 跨租户数据访问，租户隔离失效。 |
| **建议** | 1) `Auth` 中间件应始终清除并设置 `X-Aero-Tenant` 标头，而不是信任传入的标头。2) `authenticateBearer` 正确地使用密钥的租户覆盖标头，但仅当密钥租户不是 `"*"` 时才覆盖（第 86-88 行）。`"*"` 路径允许客户端指定任何租户。3) 对于管理员密钥（`tenant="*"`），要求在请求标头中显式设置租户，而不是允许任意值。4) 考虑在 `Auth` 中间件之前不将 `X-Aero-Tenant` 传播到 `TenantFrom()`。 |
| **工作量** | S（< 1 天） |

### 发现 #5 — 认证被禁用时绕过路径暴露管理端点

| 字段 | 描述 |
|-------|-------------|
| **类别** | 授权 |
| **严重性** | **中** |
| **标题** | 当认证被禁用时，绕过路径 `/healthz`、`/readyz`、`/metrics` 仍然向管理端点公开 |
| **位置** | `internal/auth/auth_middleware.go:30-32`（`isBypassPath`） |
| **描述** | 绕过路径列表包括 `/healthz`、`/readyz`、`/metrics`、`/openapi.json`、`/docs` 和 `/ui`，但**这些端点中有些可能暴露敏感信息**： - `/openapi.json` 揭示了完整的 API 表面、端点结构和参数——这是一种侦察映射 - `/docs` 提供一个交互式 API 文档页面，允许任何人探索 API - `/ui` 提供一个 Web 界面，在认证禁用时（与 `Auth` 一样）不需要任何凭证。虽然这是有意为之（`Auth` 禁用时的 MVP 行为），但在任何面向互联网的部署中，将认证禁用会使 `/ui` 和 `/docs` 暴露，没有认证。 |
| **攻击场景** | 攻击者发现一个启用了 `AUTH_KEYS=""`（认证禁用）的 aero-vault 实例 → 访问 `/docs` → 使用 Swagger UI 调用任何 API 端点 → 读取、写入或删除所有数据。 |
| **影响** | 数据泄露、数据丢失、完全系统控制。 |
| **建议** | 1) 添加一个独立的强制门控：即使 `Auth` 被禁用，在面向公众的部署中，管理/写入端点也要求令牌。2) 默认情况下，在 `AUTH_KEYS=""` 时绑定到 localhost（`APP_ADDR="127.0.0.1:8080"`）。3) 记录文档说明如果没有配置认证，则永远不要暴露在网络上。 |
| **工作量** | S（< 1 天） |

### 发现 #6 — `_aero_` 元数据前缀注入

| 字段 | 描述 |
|-------|-------------|
| **类别** | 输入验证 |
| **严重性** | **严重** |
| **标题** | 客户端提供的可以 `_aero_` 为前缀的元数据，覆盖内部系统键 |
| **位置** | `internal/api/rest/handler.go:848-866`，`internal/api/s3compat/handler.go:700-718`，`internal/service/file.go:105-120`（`validateMetadata`） |
| **描述** | 架构文档（B1）指出了这个漏洞。客户端提供的元数据键可以 `_aero_` 开头，这**保留用作系统内部使用的命名空间**（例如，`_aero_content_encoding`、`_aero_legal_hold`）。客户端可以通过存储 `_aero_content_encoding: gzip` 来欺骗系统在 GET 时解压，或注入其他 `_aero_` 元数据来篡改系统行为。`validateMetadata` 函数仅跳过检验但允许写入。 |
| **攻击场景** | 攻击者上传一个对象，其元数据键为 `_aero_content_encoding: gzip` 但内容是未压缩的 → GET 时系统输出带有 `Content-Encoding: gzip` 标头的未压缩数据 → 客户端浏览器解压并显示乱码或触发解压漏洞。攻击者可以注入 `_aero_legal_hold: ON` 以阻止删除（如果法律保留检查使用了这个键）。 |
| **影响** | 内容类型混淆，潜在的安全漏洞链，绕过合规性控制。 |
| **建议** | 在持久化之前（在 `Put` 路径中）剥离或重命名以 `_aero_` 为前缀的客户端提供的元数据键。在 `validateMetadata` 或 `service.Put` 中：</br>`for k := range meta { if strings.HasPrefix(strings.ToLower(k), "_aero_") { delete(meta, k) } }` |
| **工作量** | S（< 1 天） |

### 发现 #7 — S3 复制源路径缺乏验证

| 字段 | 描述 |
|-------|-------------|
| **类别** | 输入验证 |
| **严重性** | **高** |
| **标题** | `x-amz-copy-source` 标头中的路径遍历 |
| **位置** | `internal/api/s3compat/handler.go:115`（`copyObject`） |
| **描述** | S3 `CopyObject` 操作从 `x-amz-copy-source` 标头读取源路径。如果此路径没有得到适当的清理，攻击者可能能够使用路径遍历遍历（如 `../`）读取或复制不同桶或租户的对象。 |

| **工作量** | S（< 1 天） |

### 发现 #8 — 无速率限制的桶策略评估

| 字段 | 描述 |
|-------|-------------|
| **类别** | 输入验证 / DoS |
| **严重性** | **低** |
| **标题** | 每个请求都解析桶策略 JSON，导致拒绝服务风险 |
| **位置** | `internal/api/rest/handler.go:42-56`（`checkBucketPolicy`），`internal/api/s3compat/handler.go:73-85`（`checkBucketPolicy`） |
| **描述** | 每个 API 请求都从数据库加载桶配置，解析策略 JSON，并评估策略。缺乏缓存意味着攻击者可以以足够高的速率通过策略解析来压垮服务器。高 CPU 利用率的策略（大型条件块、大量语句）可能被利用于拒绝服务。 |
| **攻击场景** | 攻击者创建一个具有许多复杂策略语句的桶 → 以高速率向任何对象/桶路径发送请求 → CPU 花费解析和评估策略 → 对其他租户的拒绝服务。 |
| **影响** | 通过 CPU 耗尽导致的拒绝服务。 |
| **建议** | 1) 使用 `lru.Cache` 或 TTL 缓存来缓存已解析的桶策略（键：`tenant:bucket`）。2) 对策略评估计算添加时间预算，并记录/拒绝超过预算的请求。 |
| **工作量** | S（< 1 天） |

## 3. 加密

### 发现 #9 — 缺少密码学算法绑定（JWT 算法混淆风险）

| 字段 | 描述 |
|-------|-------------|
| **类别** | 加密 |
| **严重性** | **高** |
| **标题** | JWT 验证器在签名验证前不会将算法绑定到预期的算法上 |
| **位置** | `internal/auth/jwt.go:64-76`（`decodeJWTHeader`），第 105-115 行（`Verify`） |
| **描述** | `Verify` 方法首先验证签名（使用服务器秘密密钥进行 HMAC），然后检查 `alg` 头。虽然当前仅支持 HS256，但结构缺乏对算法绑定的明确架构支持。如果添加了非对称算法（RS256、ES256），`decodeJWTHeader` 会接受它（`strings.ToUpper(h.Alg) != "HS256"` 会失败），但签名验证逻辑不会切换。经典的"算法混淆"攻击允许攻击者使用 HS256 的 RSA 公钥制作令牌。 |

| **攻击场景** | 将来添加 RS256 → 攻击者获取公钥 → 制作一个带有 `alg: "HS256"` 和任意声明的令牌 → 使用 RFC 中概述的已知混淆技术，使用公钥作为 HMAC 秘密签名 → 通过 `Verify` 检查 → 完全认证绕过。 |
| **影响** | 如果系统发展到支持多个算法，完全的令牌伪造。 |
| **建议** | 在 `JWTVerifier` 中添加一个明确的 `allowedAlgorithm` 字段，并在调用 `verifySignature` 之前检查：</br>`if v.allowedAlg != "" && h.Alg != v.allowedAlg { return errors.New("jwt: algorithm mismatch") }`。在 `NewJWTVerifier` 中为 HS256 设置，并拒绝任何其他算法。 |
| **工作量** | S（< 1 天） |

### 发现 #10 — SHA256 已弃用于 API 密钥哈希

| 字段 | 描述 |
|-------|-------------|
| **类别** | 加密 |
| **严重性** | **低** |
| **标题** | 持久化 API 密钥使用 SHA-256 进行哈希，没有盐值（sk salt），使得彩虹表攻击变得可行 |
| **位置** | `internal/auth/store.go:34-38`（`HashToken`） |
| **描述** | 持久化 API 令牌使用 `sha256.Sum256([]byte(token))` 进行哈希。没有每个密钥的盐值或慢速哈希函数（bcrypt、scrypt、argon2）。如果令牌空间很小（短令牌），攻击者可以在数据库泄露前预先计算彩虹表。 |
| **攻击场景** | 数据库泄露（SQLite 或 Postgres）→ 攻击者获得 API 密钥哈希 → 对短令牌运行字典攻击 → 恢复明文 API 密钥 → 认证绕过。 |
| **影响** | 数据库泄露后，如果令牌较弱，可能恢复 API 密钥。 |
| **建议** | 1) 对每个密钥使用一个长的、加密随机的 API 密钥（建议：32 字节，通过 `crypto/rand` 生成）。2) 添加一个每个密钥的盐值与 SHA-256 一起使用，或迁移到 argon2id。3) 记录文档说明 API 密钥应至少为 128 位熵（例如，32 字节十六进制）。 |
| **工作量** | S（< 1 天，添加盐值），M（1-3 天，迁移到 argon2） |

### 发现 #11 — 缺少 TLS 配置 / 默认不安全

| 字段 | 描述 |
|-------|-------------|
| **类别** | 加密 |
| **严重性** | **高** |
| **标题** | 服务器没有要求或配置 TLS；默认绑定到 `:8080`（HTTP） |
| **位置** | `internal/config/config.go:47`（`Addr: getEnv("APP_ADDR", ":8080")`），`internal/config/config.go` 中没有 `TLS` 配置结构体 |
| **描述** | 服务器默认监听纯 HTTP `:8080`。没有 `TLS` 配置结构体（没有 `CERT_FILE`/`KEY_FILE` 环境变量）。所有 API 密钥、JWT 令牌和 SigV4 凭证都以明文形式通过网络传输。虽然这可以被代理（nginx、TLS 终止反向代理）解决，但缺乏内置的 TLS 支持意味着默认配置永远不会安全。HTTP 上的 SigV4 签名仍然允许重放攻击并且可以解密。 |
| **攻击场景** | 攻击者在网络上（共享网络、云 VPC 内部、恶意 wifi）→ 嗅探 HTTP 流量 → 捕获 API 密钥（`Authorization: Bearer ...`）、JWT 令牌、SigV4 请求 → 重放或解密。 |
| **影响** | 所有凭证泄露，完全的认证绕过，所有数据泄露。 |
| **建议** | 1) 添加 TLS 配置（`TLS_CERT_FILE`、`TLS_KEY_FILE`）并在配置时提供 HTTPS。2) 记录文档说明生产环境必须使用 TLS（通过内置支持或上游代理）。3) 考虑添加 `Strict-Transport-Security` 头。 |
| **工作量** | M（1-3 天） |

### 发现 #12 — SSE 主密钥来自环境变量

| 字段 | 描述 |
|-------|-------------|
| **类别** | 加密 |
| **严重性** | **高** |
| **标题** | 服务器端加密主密钥以明文形式存在于环境变量中 |
| **位置** | `internal/config/config.go:66`（`SSEKey: getEnv("STORAGE_LOCAL_SSE_KEY", "")`），`internal/storage/encrypt.go:80-84`（`masterKeyLen = 32`） |
| **描述** | SSE 加密的主密钥通过 `STORAGE_LOCAL_SSE_KEY` 环境变量提供。它以明文形式存在于 /proc/pid/environ、核心转储以及进程内存中。与 API 密钥类似，这个密钥保护所有静止对象数据，但没有任何形式的秘密包装。 |
| **攻击场景** | 获得代码执行或主机访问权限 → 提取 `STORAGE_LOCAL_SSE_KEY` → 解密存储中的所有对象 → 大规模数据泄露。 |
| **影响** | 所有加密对象被完全解密。 |
| **建议** | 1) 记录文档说明 `SSEKeyfile`/`SSEKeyURL` 作为比环境变量更安全的替代方案。2) 使用信封加密（已经存在 `KMS wrapper` 路径）作为默认设置。3) 考虑在启动后使用 `memguard` 或通过映射只读页面对密钥进行进程内存清零（Go 兼容性是挑战）。 |
| **工作量** | M（1-3 天） |

## 4. 会话管理

### 发现 #13 — 缺少访问令牌撤销（JWT）

| 字段 | 描述 |
|-------|-------------|
| **类别** | 会话管理 |
| **严重性** | **高** |
| **标题** | JWT 令牌在到期前不能被撤销；没有撤销列表或令牌黑名单 |
| **位置** | `internal/auth/jwt.go:105-140`（`Verify` —— 检查过期时间和签名，不检查撤销状态） |
| **描述** | JWT 一旦签发，在到期前无法撤销。没有撤销检查机制（无黑名单、无布隆过滤器）。如果 JWT 泄露（或被恶意签发的令牌），攻击者可以一直使用直到令牌过期。`exp` 声明的默认设置是**无限制的**，因为 `Sign` 只在 `c.TTL > 0` 时设置 `Exp`（`jwt.go:168-169`）。调用者可能意外签发永不过期的令牌。 |
| **攻击场景** | JWT 泄露 → 没有撤销机制 → 攻击者使用泄露的令牌 <攻击者> 直到手动轮换 `AUTH_JWT_SECRET` → 可能被窃取的令牌会造成长期的未经授权访问。 |
| **影响** | 泄露的 JWT 令牌无法撤销，导致长期认证绕过。 |
| **建议** | 1) 在 `Sign` 中强制设置 `exp` 声明：如果 `c.TTL <= 0` 则拒绝，或者设置合理的默认值（例如 1 小时）。2) 添加一个可选的 JWT 黑名单（库表 + 检查 `jti` 声明）。3) 使用短 TTL（分钟级别）并依靠刷新令牌。 |
| **工作量** | M（1-3 天） |

### 发现 #14 — SigV4 预签名 URL 过期时间过长

| 字段 | 描述 |
|-------|-------------|
| **类别** | 会话管理 |
| **严重性** | **低** |
| **标题** | 预签名 URL 过期时间没有上限 |

## 6. STRIDE 威胁模型

### 发现 #18 — 桶策略中的 `Condition` 评估是不完整的

| 字段 | 描述 |
|-------|-------------|
| **类别** | 威胁模型（欺骗 / 权限提升） |
| **严重性** | **高** |
| **标题** | `Policy.Eval` 只检查 `SourceIp` 条件；`StringLike`、`Bool`、`Date` 条件被忽略 |
| **位置** | `internal/auth/policy.go:95-107`（`Eval` -> `matchesConditions` 仅检查 `IpAddress` 和 `NotIpAddress`） |
| **描述** | `Policy.Eval` 方法委托给 `Statement.matchesConditions`，后者只处理 `IpAddress` 和 `NotIpAddress` 条件运算符。在 `Condition` 块中使用的所有其他 AWS IAM 条件键（`StringEquals`、`Bool`、`DateLessThan`、`ArnLike` 等）都被忽略。这意味着一个旨在允许基于 IP 的写入但要求 `aws:SecureTransport` 为 `true` 的桶策略，实际上会允许来自任何 IP 的写操作（`SecureTransport` 检查被忽略）。 |

| **攻击场景** | 管理员设置桶策略：`"Condition": {"Bool": {"aws:SecureTransport": ["true"]}}` → 策略被解析但 `Bool` 条件在 `eval` 中被忽略 → 来自非 TLS 连接（例如，公开 wifi）的 HTTP 请求允许访问 → 中间人攻击可以窃取/修改数据。 |
| **影响** | 配置的桶策略未按预期强制执行，导致过于宽松的授权。 |
| **建议** | 1) 将 `matchesConditions` 更新为使用 `condition.go:344-350` 中的完整 `CompileConditionSet` 函数。2) 添加对所有条件运算符的支持，包括 `Bool`（用于 `aws:SecureTransport`）、`DateLessThan`（用于过期时间）和 `StringLike`（用于 `aws:Referer`）。3) 如果条件运算符无法评估，则添加一个安全失败的 `false` 拒绝行为。 |
| **工作量** | M（1-3 天） |

### 发现 #19 — 签名验证不检查流式主体签名（SigV4 流式传输）

| 字段 | 描述 |
|-------|-------------|
| **类别** | 威胁模型（篡改） |
| **严重性** | **严重** |
| **标题** | `decodeStreamingBody` 解码流式负载但不重新验证每个块的签名 |
| **位置** | `internal/auth/sigv4_chunk.go:12-22`（`decodeStreamingBody`） |
| **描述** | 当使用 `STREAMING-AWS4-HMAC-SHA256-PAYLOAD` 时，每个块都有其自己的签名，构成完整的签名链。`decodeStreamingBody` 从请求体中剥离块格式，但**不验证每个块的签名**。它记录了这一点（"不重新验证"）。这意味着攻击者可以篡改块式上载的正文，而不会使签名无效——整个请求的完整性由种子签名保护，但部分上传可以被操纵。 |
| **攻击场景** | 受害客户端通过 `aws s3 cp` 上传一个大型文件（默认分块），放入中间人 → 攻击者修改传输过程中的块数据 → 种子签名通过（它只覆盖标头和种子）→ 服务器存储被篡改的数据 → 受害者检索损坏/恶意文件。 |
| **影响** | 存储损坏、服务用户的恶意软件注入、信任破坏。 |
| **建议** | 1) 实施每个块的签名验证（AWS 规范：`chunk-signature=HMAC(prev_sig, ...)`）。2) 或者，完全禁用流式签名验证并标记它，记录文档说明流式正文在没有块签名验证的情况下不被信任。3) 在收到完整正文后计算 `Content-MD5` 并验证它。 |
| **工作量** | L（> 3 天，用于正确的块签名验证） |

### 发现 #20 — 重放攻击：缺乏 SigV4 请求时间窗口

| 字段 | 描述 |
|-------|-------------|
| **类别** | 威胁模型（欺骗 / 篡改） |
| **严重性** | **高** |
| **标题** | SigV4 请求不会验证 15 分钟时间窗口 |
| **位置** | `internal/auth/sigv4.go:117`（`verifyHeader`） |
| **描述** | AWS SigV4 规范要求服务器验证 `X-Amz-Date` 在服务器时间 ±15 分钟内。这可以防止重放攻击。当前的实现解析 `amzDate` 但不验证它是否在合理的时间窗口内。预签名 URL 通过检查 `signedAt.Add(secs)` 验证过期时间，但 `verifyHeader` 完全跳过时间检查。 |
| **攻击场景** | 攻击者捕获一个已签名的 SigV4 `PUT /bucket/key` 请求（具有有效签名）→ 在一小时、一天、一周后重放相同请求 → 服务器接受它，因为它不验证请求年龄 → 导致重复的写入操作，可能覆盖数据。 |
| **影响** | 请求重放导致重复写入、数据损坏或非幂等操作。 |
| **建议** | 在 `verifyHeader` 中添加基于 `X-Amz-Date` 的 ±15 分钟时间窗口检查：`if delta := time.Since(signedAt); delta > 15*time.Minute || delta < -15*time.Minute { return Key{}, errors.New("sigv4: request expired") }` |
| **工作量** | S（< 1 天） |

### 发现 #21 — 租户映射的 DoS 攻击：无限制的桶创建

| 字段 | 描述 |
|-------|-------------|
| **类别** | 威胁模型（拒绝服务） |
| **严重性** | **中** |
| **标题** | 速率限制器按租户工作，但桶策略按请求评估，没有每个桶的速率限制 |
| **位置** | `internal/middleware/ratelimit.go:70-93`（`Allow`） |
| **描述** | 全局和 AI 速率限制器按租户工作（使用 `X-Aero-Tenant` 作为键）。但是，一个`*`（管理员）租户密钥可以以任何租户身份发送请求（通过设置 `X-Aero-Tenant`），这意味着具有管理员访问权限的恶意用户可以在共享速率限制桶中压垮特定的租户。此外，桶创建（`PUT /bucket/`）没有速率限制，允许数十亿桶的 DoS 攻击。 |
| **攻击场景** | 攻击者使用管理员密钥向 `X-Aero-Tenant: victim` 以每秒 100k 个请求发送请求 → 受害者租户的速率限制桶被填满 → 合法用户被速率限制 → 拒绝服务。或者：攻击者创建 100 万个桶 → 数据库大小增加，读取性能下降，存储成本增加。 |
| **影响** | 共享租户速率限制桶上的拒绝服务，数据库存储 DoS。 |
| **建议** | 1) 基于底层身份（密钥哈希）而不是客户端控制的标头添加速率限制。2) 对桶创建添加每个租户的速率限制。3) 限制每个租户的最大桶数。 |
| **工作量** | M（1-3 天） |

### 发现 #22 — 审计日志：授权决策不可审计

| 字段 | 描述 |
|-------|-------------|
| **类别** | 威胁模型（否认） |
| **严重性** | **中** |
| **标题** | 授权拒绝不记录审计事件 |

### 发现 #24 — `Content-MD5` 标头未经 Base64 解码验证

| 字段 | 描述 |
|-------|-------------|
| **类别** | 输入验证 / 数据完整性 |
| **严重性** | **中** |
| **标题** | `Content-MD5` 标头被接受并转发，但未经服务器验证 |
| **位置** | `internal/api/rest/handler.go:83`（`ContentMD5: r.Header.Get("Content-MD5")`），`internal/service/file.go`（`PutOptions.ContentMD5`） |
| **描述** | `Content-MD5` 标头（一个 Base64 编码的 MD5 哈希）由 REST/S3 处理程序提取并转发到 `service.Put`，但似乎没有服务器端验证上传的正文是否与提供的 MD5 哈希匹配。AWS S3 验证在 Put 时提供的内容 MD5 哈希。忽略它意味着损坏的上传不会被检测到。 |
