## 方向一：对象锁合规治理与 Legal Hold 案件管理框架

**最强的合规差异化方向。** 当前实现确实是二进制标记级别的 MVP——`_aero_legal_hold` 作为 metadata key 而非独立实体，这意味着：

- 无法回答 "当前系统中有多少对象处于 legal hold 状态？"（需要扫描全部对象的 metadata 字段）
- Hold 与案件无关联——律师无法出具 "案件 #12345 涉及的 15 个对象当前 held" 的报告
- 无 Compliance 模式意味着运维人员可以 `PUT metadata._aero_legal_hold = "OFF"` 绕过

**建议补充的架构考量：**

| 维度 | 补充建议 |
|------|---------|
| **数据模型** | `legal_holds` 表不应只有 1:N，还应引入 `hold_cases` 表（1:N:hold_events）。保管人（custodian）应该可以是用户引用（`user_id`）或自由文本（外部律师）——不能只支持已注册用户 |
| **性能** | `checkLockBeforeOverwrite` 当前 O(1)，引入 legal_holds 表后变为 O(n_holds)。建议对活跃 legal hold 数量做软限制（默认 ≤100/对象），超过则拒绝新增 hold 而非默默承受扫描开销 |
| **GC 危险** | 文档正确指出 compliance hold 下的对象永远不可删除。但当前的 `hardDeleteObject` 路径被 `reconcile`、`s3compat batch-delete`、`REST delete` 三条路径调用。**必须统一准入点**，否则某条路径可能遗漏检查 |
| **审计事件** | 文档建议 `hold_events` 表——这个表应作为 `audit_log` 的补充而非替代。Hold 操作应同时写入 `audit_log`（管理审计）和 `hold_events`（合规快速查询） |

**一个未被文档覆盖的风险：** Legal hold 与版本控制的交互。如果一个对象有 5 个版本，legal hold 施加在最新版本上——旧版本是否可以被删除？按照 S3 的语义：legal hold 作用在对象（所有版本）上，而非单个版本。当前版本化实现中每个版本独立锁定，需要确认这个语义。

## 方向二：服务端对象变换管线与预览生成框架

**性价比最高的方向。** 从 thumbnail 到通用变换管线的跃迁路径清晰，3 周 MVP 的估算合理。

**建议补充的技术决策：**

| 决策点 | 建议 |
|--------|------|
| **变换引擎** | 文档在 "内置 Go 标准库 / Libvips / HTTP 远程" 三者间摇摆。建议走 **Libvips（vips-go 绑定）** 路线：Go 标准库缺失 WebP/AVIF/HEIC，HTTP 远程引入可用性风险。Libvips 是 Cloudinary 和 imgix 的底层引擎，成熟度无需担心。进程外调用增加复杂度但避免 CGo 编译问题 |
| **变换声明格式** | 文档提到 `?w=200&format=webp` 参数风格。建议同时支持 **声明式变换链**：`?x-actions=resize:w_200,fit_cover;format:webp;watermark:pos_se,text_copyright`——用逗号分隔的变换步骤链，给客户端细粒度控制的同时保留服务端缓存能力 |
| **缓存键** | 文档建议 `{storage_key}?w={w}&h={h}&format={fmt}`。但变换参数顺序无关性需要规范化：`?w=200&h=100&format=webp` 和 `?format=webp&h=100&w=200` 应命中同一缓存。**建议对缓存键做参数排序 + 规范序列化** |
| **派生存储** | 文档建议不计入租户配额——正确。但还需考虑派生对象的 GC：如果原始对象被删除，其所有派生缓存应该被异步清除。可以在 `object.deleted` 事件中注册一个 `DerivativeCleaner` worker |

**一个未被强调的 ROI：** WebP/AVIF 转码对移动端用户的带宽节省在 40-60%，而实现成本极低（Libvips 一行 `vips_webpepe_save`）。如果 aero-vault 面向图片密集场景（社交媒体、电商），这是最能直接提升用户体验的功能。

## 方向三：分布式速率限制与多层级配额治理平面

**架构影响最大的方向。** 文档对当前缺陷的分析（每进程独立、无权重模型、无分层继承）精准。但有几点需要深入讨论：

**Postgres 作为分布式限流后端的陷阱：**

文档推荐 "Postgres 优先（零新增依赖）"，但这个选择需要审视：

```
1. 限流是高频路径：每请求 1 次调用
2. Postgres UPDATE 行锁在并发 >100 时延迟抖动明显
3. 限流后端不可达时的降级策略（文档已提及）需要在代码中实现且测试
```

如果 aero-vault 的部署规模预期超过 3-5 个副本（每个副本 >500 RPS），Postgres 行锁会成为瓶颈。建议的演进路径：

```
MVP（方向三）：Postgres tx `SELECT ... FOR UPDATE` + 租户级别 RPS
├── 限流精度：秒级窗口
├── 降级：本地 token-bucket fallback
└── 不适合：>5 副本 / >2000 全局 RPS

V2：接入 Redis Sliding Window Log
├── 精确到毫秒
├── 支持 SCRIPT LOAD 原子操作
└── Redis 不可达 → 降级到 Postgres → 降级到本地

V3（如需）：Redis + CRDT 计数器（无中心节点）
```

**成本模型的可配置性：**

文档列出了硬编码的权重表。在实际部署中，不同租户可能需要不同的成本权重——图片存储场景的 `PUT` 权重应该高于文档存储场景。建议权重模型可配置（通过配置或租户级设置），而非硬编码。

**突发银行的经济学：**

文档提到 "每秒未使用的 RPS 额度按 50% 累积到突发银行"。但需要明确银行累积的上限——如果租户在低负载时段累积了 1 小时的额度，然后在 1 秒内全部消耗，对后端的影响与没有限流一样。建议：

```
突发银行上限 = min(burst_max_seconds × base_rps, max_burst_absolute)
其中 burst_max_seconds 默认 30（最多累积 30 秒的额度）
```

这样突发仍然被控制在一个安全窗口内。

## 方向四：统一搜索查询语言——跨元数据与跨模态内容检索

**差异化最大也最复杂的方向。** 文档的 `v1/query` DSL 设计合理，跨模态（元数据 + 语义 + 关键词）的思路正确。但有几个架构风险需要前置于实现：

**查询执行计划的规划是最大风险：**

文档列出了三种执行模式（Filter→Content、Content→Filter、Parallel→RRF），这是正确的。但实际实现中，选择哪种模式需要**基于 selectivity 的代价估计**——如果没有查询规划器，"选择正确执行模式" 的复杂度可能超过查询语言本身的实现。

建议 **避开代价优化，采用确定性策略**：

```go
// 第一阶段：固定策略而非代价优化
switch {
case hasContentQuery && !hasMetadataFilter:
    mode = "content_only"                    // 纯语义/BM25 搜索
case !hasContentQuery && hasMetadataFilter:
    mode = "metadata_only"                   // 纯元数据查询
case hasContentQuery && hasMetadataFilter && metadataIsHighlySelective:
    mode = "filter_then_content"             // 元数据过滤后内容搜索
default:
    mode = "rrf"                             // 并行融合（兜底）
}
```

`metadataIsHighlySelective` 可以用简单启发式（如：有 `eq` 字段过滤 + 有 `gt` 大小过滤 = 高选择性；仅有 `after` 时间过滤 = 低选择性）。

**跨租户搜索的鉴权风险：**

文档提到跨租户搜索需要 operator/管理角色。但跨租户搜索的**结果可见性**需要额外关注——一个搜索结果可能包含来自租户 A 和租户 B 的对象，但两个租户看到的应该是对方的对象被 mask 掉（显示 "存在匹配对象但不显示内容"）还是完全不可见？建议跨租户搜索只在管理/审计场景下可用，普通租户请求即使指定了多 tenant 也返回错误。

**与既有 API 的兼容性：**

文档的 `/v1/query` 是新端点。但 aero-vault 已有 `/v1/search`（AI 内容搜索）、`/v1/files`（元数据列举）。建议 `/v1/query` 在内部**重用** `Search.Query` 和 `ListObjects` 的执行路径，而不是平行新增一套执行引擎。这样 `/v1/query` 可以逐渐替代旧端点，而非增加维护负担。

## 方向五：异步写入缓冲与优雅降级写入路径

**韧性提升最大的方向，但也是最容易引入复杂性的方向。**

**写入后读一致性是需要预先设计好的：**

文档写到了 "缓冲中对象在持久化前被读取——从缓冲中提供"。这个设计决策影响整个读取路径：

```go
// 当前读取路径（同步）：
Get(key) → store.Get(key) → 返回流

// 异步缓冲后的读取路径（需要新增）：
Get(key) → {
    // 1. 检查 L1 内存 buffer 是否有待持久化的写入
    // 2. 检查 L2 WAL 是否有待持久化的写入
    // 3. 以上都没有 → store.Get(key)
}
```

这意味着 `Get` 路径需要新增对 buffer 的搜索。对于内存 buffer（L1），这是 O(1) map 查找。对于 WAL（L2），这意味着 SQLite 查询。**异步写入模式下，`Get` 延迟会增加约 0.5-2ms**（SQLite 查询时间）。需要明确这个延迟增加是否可以接受，或者只在特定模式下（如 `X-Write-Mode: async` 的响应中有 `Location` header 指示客户端使用 Job API 轮询）放弃读-写一致性。

**推荐更务实的路径：**

`X-Write-Mode: async` 返回 `202 + Location` 后，客户端应通过 `/v1/jobs/{id}` 轮询结果。在异步写入到最终持久化之间的窗口内，`GET` 请求**不保证**读到刚刚写入的对象。这样可以：

1. 保持 `Get` 路径的延迟不变
2. 避免 L1/L2 buffer 搜索的复杂度
3. 符合 REST 的 202 Accepted 语义（"请求已接受但尚未完成"）

**WAL 磁盘满的处理：**

文档提到了监控告警。但还需要一个更关键的策略：**WAL 所在的磁盘不应与对象存储磁盘共用**。如果对象存储磁盘满了导致写入进入 WAL 缓冲，WAL 所在的系统盘不应该受牵连。在部署文档中应明确要求 WAL 路径（`WRITE_BUF_WAL_DIR`）与对象存储路径分离。

**幂等性去重的实例：**

文档提到了 "用 idempotency-key 去重"。这个已经在系统中实现了——`Idempotency-Key` 请求头。异步写入缓冲可以直接复用这个机制：`Idempotency-Key` 相同则自动跳过重复持久化。这是文档提到的 "已有基础设施复用" 的最佳示例。

### 优先级调整建议

文档的优先级排序基本合理，但建议微调：

| 排序 | 方向 | 文档建议 | 我的建议 | 理由 |
|------|------|---------|---------|------|
| **1** | 服务端变换管线 | ✅ P1 | ✅ P1 | 3 周 MVP，ROI 最高，无外部依赖 |
| **2** | 对象锁合规治理 | P1 | **P1（与变换管线并列）** | 合规硬需求不能等变换管线完成后再开始。建议两方向并行，共享同一个 Sprint |
| **3** | 分布式配额平面 | P2 | **P1** | 文档的 P2 低估了影响——如果 aero-vault 要部署到多副本生产环境，当前每进程限流是**阻塞项**。这应该是 Phase 1 的 P1 |
| **4** | 统一搜索查询语言 | P2 | **P2** | 正确。需要前三个方向的基础设施 |
| **5** | 异步写入缓冲 | P3 | **P3** | 正确。复杂性最高，收益在初期不明显。建议作为 Phase 2 的投入 |

### 未覆盖的风险与依赖（跨方向）

| 风险 | 影响方向 | 建议 |
|------|---------|------|
| **存储后端抽象层在变换/缓冲场景下的表现不足** | 方向二、五 | 当前 `storage.Storage` 接口的 `Get` 返回 `io.ReadCloser`。变换管线需要 `io.ReadSeeker`（libvips 需要）。异步缓冲需要 `Put` 支持延迟写入（先存后传）。接口可能需要调整 |
| **迁移文件版本增长** | 方向一（新增 legal_holds 表） | 当前已有 48 对迁移文件。新增 `legal_holds` 表需要注意 I2 约束——每次迁移都要双文件（sqlite + postgres），且不能编辑已有的迁移 |
| **租户级默认值的传播** | 方向一（租户默认保留）、方向三（分层配额） | 当前 `ObjectLockSeconds` 是 bucket 级别的配置。如果新增租户级默认保留策略，需要决定：bucket 设置是否覆盖租户默认值？覆盖的方向是什么？建议：租户默认值作为 bucket 未设置时的 fallback，bucket 设置优先 |
| **OpenAPI 规范的同步** | 方向二、四 | 新增的 `/v1/transform` 和 `/v1/query` 端点需要同步更新 `openapi.json`。文档未提及，但这是 CI gate 的一部分 |
