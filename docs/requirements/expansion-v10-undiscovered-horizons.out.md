## 对《AeroVault 高价值扩展方向（第十期）》的审阅意见

### 总体评价

文档质量高、结构清晰、代码锚点精准、边界情况考虑充分。五选方向的企业级合理性和架构可增量性论证扎实。但存在**若干事实性偏差和遗漏**，需要修正后方可作为下一阶段的决策输入。

---

### 1️⃣ 事实准确性核查

#### 问题一：方向 #4（API 版本治理）— "零覆盖" 不成立

文档声称方向 #4 在前九期中「**零覆盖**」，但 `expansion-v4.md` **已用完整章节**讨论 API 版本治理。

我审阅了 `docs/requirements/expansion-v4.md:325-385+`，内容包括：
- **完整的为什么需要分析**（单版本号的风险、无弃用框架、无标准化分页、SDK 手动维护等问题）
- **10 行代码锚点表**（涵盖了 `router.go`、`handler.go`、`dto.go`、`ratelimit.go`、`openapi.json`、三个 SDK）
- **架构蓝图**（两种方案对比：Accept-Version header vs URL 路径版本，含中间件实现伪代码）
- **弃用框架**（RFC 8594 Sunset/Deprecation headers 的设计）

这不是"骨架提及"，而是**系统性分析**。虽然 v4 的分析从未被实现（这是有价值的发现），但文档在"既有文档覆盖"一栏标注「**零覆盖**」是事实错误。建议改为：`v4 有完整架构蓝图但从未落地`。

#### 问题二：方向 #2（对象级访问审计）— "零覆盖" 定性偏严

在 reviewed scope 内，`analysis-v3.md` 和 `analysis-v6.md` 讨论了 **audit_log 的不可变性和保留策略**，`expansion-directions.md` 提及了 `share_access_logs`。但确实**没有系统讨论过"对象级数据访问追踪"**（谁在何时读取/写入了哪个对象）这一独立概念。现有 audit 讨论聚焦于 admin 管理操作日志的加固，而非扩展至数据层面。

所以**严格来说，零覆盖的是"对象级访问追踪"这个具体功能**，而不是"审计"这个广义概念。建议文档明确标注这一点，避免误读。

#### 问题三：方向 #1（SSE-C）— 对 v3 的描述略有偏差

文档称"仅 v3 一行提及"SSE-C 互斥""。实际 v3 有两处提及（line 220 的加密优先级表和 line 291 的边界情况），但**确实没有系统分析**。定性基本准确。

### 3️⃣ 方向优先级再评估

在修正上述事实偏差后，重新审视优先级排序：

| 原排序 | 方向 | 我的建议 | 理由 |
|--------|------|---------|------|
| #1 | CSE/SSE-C | **保持 #1** ✅ | 安全错觉 + S3 兼容性最后缺口，论证充分 |
| #2 | 对象级审计 | **保持 #2** ✅ | SOC2/PCI/HIPAA 合规准入，独立价值成立 |
| #3 | API 版本治理 | **升至 #3** 🔼 | 这不是新发现而是**未执行的决策**。v4 已有蓝图却迄今未落地，说明拦路虎不是分析不足而是执行阻力。把已识别但未执行的路径优先级提前，比新发现的方向更有工程价值 |
| #4 | 数据迁移 | **保持 #4** ✅ | 运维刚需但不是每日必须，复杂度适中 |
| #5 | 优雅关闭 | **升至 #4 (并列)** 🔼 | K8s 滚动更新每次中断请求是生产事故，且与 #2（审计中间件）有代码层面协同效应——`TrackInFlight` 中间件和 `AuditMiddleware` 可以共用 middleware 注册机制 |

修正后排序建议：**CSE > 对象审计 > API 版本治理 > 优雅关闭 = 数据迁移**

### 4️⃣ 遗漏的技术细节

在审阅现有代码后，以下信息有助于完善文档的分析：

#### 方向 #1 SSE-C：还有另一个代码点的缺失

文档列出了 `internal/storage/storage.go` 的 `PutOptions`/`GetOptions` 缺少 `CustomerKey` 字段，但还需要考虑：

```go
// internal/storage/local_write.go 中的 ChunkedUploader
// 多分片上传场景：每个 UploadPart 必须携带相同的 SSE-C 密钥
// 当前 ChunkedUploader 是一个长期存在的状态对象（part 之间复用）
// 加入 CustomerKey 意味着状态对象需要持有密钥内存引用
```

文档在边界情况中提到了"SSE-C + multipart upload"但没有在代码锚点中标注 `ChunkedUploader`。

#### 方向 #5 优雅关闭：被忽略的 goroutine 泄漏点

文档缺少对当前代码中**未受 ShutdownManager 管理的 goroutine** 的分析：

```bash
$ grep -r "go func\|go " cmd/server/main.go | head -5
# 启动 OTel HTTP server 的 goroutine
# BM25 重建 goroutine（如果 AI_INDEX_ENABLED）
# SSE hub 的 goroutine
```

这些 goroutine 在关闭时如果不排空，会导致：
- OTel HTTP server goroutine 泄漏
- BM25 重建在关闭时可能写入已关闭的索引
- SSE hub 没有 draining 阶段的客户端通知
