### 可补充的分析视角

| 维度 | 现状 | 可深化 |
|------|------|--------|
| **方向一（多模态）与现有 `RemoteExtractor` 的关系** | 提到了远程协议可扩展，未分析 `REMOTE_EXTRACTOR` 协议的具体请求/响应格式 | 如果 `RemoteExtractor` 已经支持 `POST → plainText`，扩展为结构化响应（`{text, metadata, segments}`）只需要改协议版本号 + 解析逻辑，代码修改量很小 |
| **方向二（元数据过滤）的 filter 下推 vs 后过滤性能** | 推荐嵌入策略（下推），但没有给出规模阈值 | 建议补充：内存 BM25 后端在 <10 万 chunk 时后过滤可接受；Qdrant/pgvector 必须下推 |
| **方向三（去重）与 WORM/对象锁的交互** | 未分析 | 若对象有 WORM 锁，共享 blob 被一个引用锁定后，其他引用是否也被锁定？建议：`RefCount` 不解锁，引用计数和 WORM 是两个维度 |
| **方向四（缓存）的 Range 请求支持** | 边界情况提到但不详细 | `CachedStorage.Get` 如果只缓存完整对象，Range 请求需要从缓存读取完整内容再截取，浪费内存。建议只对完整对象 <1MB 缓存，大对象用 `ReadCloser` 旁路 |
| **方向五（active-active）的 `jobs` 表跨区域问题** | 提到 leases 不支持跨区域 | `jobs` 表也是单 DB 的——跨区域后 job pool（reconcile/GC）如何避免重复执行？需要区域级 leader 选举 |

### 实施顺序建议 — 调整点

您的建议顺序是 **② → ① → ③ → ④ → ⑤**（方向二为首）。

从**工程依赖**角度考虑，我建议微调：

```
① 多模态 AI 管线  ← 与方向二并行，无依赖
② 元数据锚定搜索  ← 与方向一并行，无依赖
④ 对象缓存层次    ← 等方向二稳定后（缓存写入路径修正需要搜索稳定）
③ 内容去重       ← 存储层变更，影响所有路径，建议单独 sprint
⑤ 主动-主动复制   ← 依赖方向④的就绪
```

方向一和方向二可以**并行开发**（不同包、不同接口），这是最大的效率机会。
