## 对优先级与范畴的审视

整体认可 P1/P2 排序。补充几个我看到的交叉点：

### P1 方向之间的依赖关系

```
元数据查询引擎 ← 事件 WAL（索引更新需要一致的事件流）
存储类生命周期 ← 缓存（GLACIER 恢复后的临时副本应进缓存）
```

元数据索引的**一致性模型**取决于 WAL 是否就位：
- 无 WAL：只能异步索引（EventBus），最大 ~1s 延迟
- 有 WAL：可以从 WAL 游标重建索引，保证不丢事件

建议**元数据查询的 MVP 先走异步 EventBus 路径**，不阻塞 WAL，等 WAL 就位后再升级一致性保证。

### 缓存层的一个关键边界问题

文档提到缓存 SSE-C 加密对象时建议**缓存密文**。这里有一个更尖锐的问题：

```
SSE-C:  每请求客户端提供密钥 → 无法跨请求共享缓存（键必须包含密钥 hash）
SSE-S3: 服务端透明加解密 → 缓存键不含密钥信息，可直接缓存
```

所以 `CachingStorage` 需要对 SSE-C 对象**降级**——不经过 L1/L2 缓存，直接穿透到后端。这个 fallback 逻辑在 `CachingStorage.Get` 的路径选择中需要提前判断。

### 存储类生命周期：一个被低估的工程难点

文档正确指出了 `STANDARD → STANDARD_IA` 仅改元数据，但**local 后端**的 `GLACIER` 降冷有实际含义吗？local FS 没有不同的存储介质（除非配置不同的挂载点）。建议：
- local 后端的 `GLACIER` = 对象标记为归档 + blob 移动到 `{root}/.archive/` 目录（OS 级冷数据提示通过 `fallocate` 标记 `FALLOC_FL_COLLAPSE_RANGE`? 不现实）
- 更实际的做法：local 的 GLACIER 只是一个**元数据标记 + 权限限制**（阻止普通 GET，需先 restore），实际节省来自用户手动将存储卷迁移到冷介质

### 文档未涉及的潜在交叉价值

**缓存 + 元数据查询：**
- 元数据查询结果可缓存（`{query_hash, tenant} → []ObjectID`），TTL 取决于元数据变更频率
- 这个缓存与现有的 AI Search 缓存 (`resultCache`) 可共用同一 `ristretto` 实例

**去重 + 存储类生命周期：**
- 如果一块数据被多个对象引用，且其中一个对象降冷到 GLACIER——块本身不能降冷（可能被其他热对象引用）
- 需要在块级维护 `min_storage_class`（所有引用对象中最低的 storage class），防止热数据依赖的冷块被归档
